# Administration

The separate apps/admin client uses dedicated identities, sessions and MFA through /admin-api. Consumer cookies and agent credentials do not grant administration access. Roles are viewer, operator and owner. Authentication and every sensitive action check the current role/state; customer ownership remains in shared library services.

Overview displays defined usage counts and operational status. Users supports bounded searching/filtering, metadata and account lifecycle actions. Connections lists only safe credential metadata and supports independent revocation. Activity shows actor, target, time, reason and outcome without private notes, resource content or credential material. Admin access is owner-only. Private libraries and impersonation are deliberately outside this release.

Bootstrap sends a single-use verification/enrolment invitation. Invite tokens use URL fragments so they are absent from HTTP request logs. Administrators establish password and TOTP, then store one-time recovery codes. TOTP follows RFC 6238 and RFC 4226; test vectors cover the implementation. Secrets are AES-256-GCM encrypted with a configured server key; passwords/codes/session/invite values are stored as hashes. Sessions have 30-minute idle and 8-hour absolute limits, with fresh authentication required within five minutes for sensitive changes. Authenticator replacement and operator-assisted recovery revoke prior sessions/codes. No default password, public admin signup or customer promotion exists.

Suspension revokes customer browser/agent credentials and pending email/OAuth grants, and blocks all authentication/token-creation paths. Restoring access preserves the library but does not restore those credentials. Support emails use standard account flows, a five-minute per-purpose cooldown and encrypted delivery jobs. Resend receives a stable idempotency key per job; delivery retries are bounded to three and terminal job payloads are erased. Sender acceptance is recorded separately from delivery failures and does not imply inbox receipt.

Deletion reuses the durable deletion journal. A committed administrative deletion-request audit precedes the journal, followed by transactional completion audit. This preserves an authorised trail even if later database work fails and the journal completes deletion on recovery. Concurrent changes cannot remove the final usable owner. Audit writes are mandatory for privileged changes and have no application edit/delete endpoint. Controlled retention removes audit records after 90 days, completed jobs after 7 days and expired sessions/invitations on startup/daily, or via the maintenance CLI.

Evidence recipes: tests/admin.test.ts and tests/browser/admin.spec.ts. Browser traces/screenshots are disabled during enrolment; screenshots are taken only on ordinary screens with disposable fixture accounts. All test schemas are disposable PostgreSQL schemas. Deployment/owner activation remains pending until recorded in docs/verification.md and docs/operations.md.

Sources: [TOTP specification](https://www.rfc-editor.org/rfc/rfc6238), [HOTP specification](https://www.rfc-editor.org/rfc/rfc4226), [Resend idempotency](https://resend.com/changelog/idempotency-keys).

The browser recipe also enrols a separate operator through an owner-issued invitation. It checks the owner-only navigation/deletion controls are absent, suspends/restores a disposable account through the operator UI, verifies the customer session was revoked, and cleans up using a new customer login. Integration checks cover independent sign-out versus disconnect actions, login rate limiting, mixed login/key/OAuth races during both suspension and deletion, journal write failure and replay after an authorised deletion transaction rolls back.

Account-scoped activity includes connection revocations via their retained opaque owner UUID, even after the revoked connection or customer has been deleted. The account filter excludes other customers. Migration 0006 adds a partial owner index for these revocation events; migration 0005 remains unchanged.


Library v2 local adaptation adds retained item counts by kind/state, private-file byte and processing counts, summary job failures and aggregate request/token/cost totals. These details sit in a collapsed Library details section. Health distinguishes configured storage/summaries from unconfigured services. Tests verify that overview responses omit filenames, URLs, titles, document bodies, prompts and generated content. This adaptation is not deployed until the coordinated Library v2 release.
